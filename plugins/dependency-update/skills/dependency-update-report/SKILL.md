# 1件の依存関係の更新のレビュー

指定された1件の依存関係の更新をレビューし、レポートを出力する。実行するのは、dependency-update skillの指揮役から任されたsubagentか、手元のsessionのユーザーである。更新対象は、ライブラリの他に、Docker image、GitHub Actions、ランタイムの事がある。コマンドやファイルの例はNode.jsのライブラリで示すので、実際の更新対象とそのエコシステムの常識に照らして読み替える。

## ファイル構成

```
{このSKILL.mdがあるディレクトリ}/
  SKILL.md       ← この手順書
  TEMPLATE.md    ← レポートの形
```

## このskillを実行する時の前提

- 実行環境の条件は、[dependency-update skill](../dependency-update/SKILL.md) の「実行環境の確認」にあるmodelの条件と同じである。レビューに入る前に自分でも確認し、満たさなければレビューもレポートの出力も行わず、満たさない条件を報告して終了する
- 次の値は、起動した時の指示に従う
  - レビューの対象。pull requestの他に、pull requestになっていないbranchや、作業ツリーの変更の事がある
  - レポートの出力先。pull requestへのコメント、ファイル、sessionへの表示等である
  - ラベルの名前、コードを読む場所、作業ディレクトリ、レポートの言語
- レビューの対象か、レポートの出力先の指示が無い時は、調査を始める前に、ユーザーと対話できる環境では欠けている値を訊く。対話できない時は、欠けている値を報告して終了する
- 判断がつかない事は、ユーザーと対話できる環境ではユーザーに訊く。対話できない時は、レポートと報告に書く
- subagentとして実行している時は、ユーザーと対話できない。同じリポジトリの別のpull requestを扱うsubagentが並走している事もあるので、指示された作業ディレクトリの外を変えない
- 行うのはレビューだけで、レポートの出力と、指示された時のラベルの付与に限る。コードの修正、commit、push、新しいpull requestの作成はしない。修正が必要な時はレポートに書く

## 調査

レポートの節ごとに書く事を、次の順に調べる。pull requestの概要欄の説明は誤っている事があるので、変更内容の根拠にしない。コードとdiffと、公式のドキュメントを根拠にする。外部のドキュメントを参照した時は、そのURLをレポートに書く。

### 更新対象の概要

READMEや公式サイトのドキュメントを読み、何を実現するために、どのような用途で使われる物かを調べる。

### バージョン情報

変更前と後のバージョンと、それぞれのリリース日時を調べる。更新先が最新版か、その先にmajor versionの更新があるかも調べる。major versionの更新では、名前の変更やリポジトリの移管が起きている事がある。

### 変更スコープ

lock fileの差分から、更新・追加・削除されたパッケージを列挙する。件数が多くても、主要な変更対象は漏れなく挙げる。更新対象との関係が明確でないパッケージの変更が含まれていたら、その旨を注記する。この時点で安全性や影響範囲は断定せず、後の節で確かめる注意点として扱う。

例: npmの `package-lock.json` なら、変更の差分からlock fileの差分を取り、個別のパッケージの周辺は `grep -C15 '<パッケージ名>' package-lock.json` で確かめられる。

### 依存関係

lock fileから、更新対象に依存している他のパッケージと、更新対象が依存しているパッケージを列挙する。

### 使用箇所とバージョン指定箇所

リポジトリ内で、更新対象や実行環境が参照・指定されている箇所を、ファイル単位で一覧にする。import文やrequire文だけでなく、設定ファイル・Dockerfile・CI設定・開発環境設定のように、バージョンが指定されている箇所も含める。名前での検索に加えて、バージョン番号での検索も行う。他の節で読んだファイルにバージョンの指定があれば、この一覧に含める。この一覧は、「コード・設定の更新」のバージョン整合性の確認の入力になる。

### 変更内容の要約

公式サイトやGitHubのrelease note、changelog、migration guideを読み、変更前と後の間にある全バージョンの変更を1つずつ確かめる。機能追加やAPIの仕様変更のうち、アプリケーション側で使っている機能に関係がありそうな物を抜き出す。

### コード・設定の更新

2つの観点を区別して確かめる。

- APIや仕様の変更に伴うコード修正。release noteやchangelogだけで正しい変更方法が分からない時は、GitHubのcommitの差分や公式ドキュメントも読む
- バージョン整合性。この更新で変わったバージョン番号を、リポジトリ内の他の箇所でも揃えるべきかを確かめる
  1. diffから、変更前と後のバージョン番号を特定する
  2. 更新対象の種別を判断する。npmパッケージ、ランタイム、Docker base image等である
  3. 揃えて同時に更新するべき箇所を、リポジトリ全体で探す。「使用箇所とバージョン指定箇所」の一覧を確かめる。例えばNode.jsのランタイムの更新では、ローカル開発環境とproduction環境でバージョンを揃える必要があり、Dockerfileだけでなく、package.jsonやpackage-lock.jsonのengines・packageManager、.nvmrc、CI設定等も確かめる
  4. 古いバージョンが残っている箇所を、レポートに書く

バージョン文字列の完全一致検索だけで問題なしとしない。範囲指定やエイリアスで管理されている場合がある。Node.jsに対応するnpmのように関連するバージョンの対応関係は、推測せず、公式ドキュメントや実際の配布物を根拠にする。外部アクセスの制限で確認できない時は、未確認としてその旨を書く。

### 興味深い更新

アプリケーションにも応用できそうな新機能の実装や概念の発明、プログラム言語や実行環境の新機能を活用した実装、開発体制の変化のような物があれば、拾う。

### 過去の失敗

このリポジトリで、更新対象に関する問題が起きた事が無いかを、pull requestとissueを更新対象の名前で検索して調べる。mergeせずにcloseした、mergeしたが不具合が出てrevertした、といった事例である。見つかったら、解決されているかを確かめる。

## 修正のcommitを含むpull requestの再レビュー

dependency-update-fixが積んだ修正のcommitを含むpull requestでは、上の調査に加えて、そのcommitの差分が、揃える箇所を列挙した文書の挙げる箇所だけに収まっている事を確かめる。収まっていなければ、結論を「修正無しでmerge可」にしない。修正のcommitのSHAと文書の場所は、起動した時の指示で渡される。

## 最終確認

レポート全体を横断して、節の間の矛盾や漏れを確かめ、見つかれば該当する節を直す。

- 他の節で読んだファイルが、「使用箇所とバージョン指定箇所」の一覧に含まれているか
- 一覧の参照箇所が、バージョン整合性の確認で全て検証されているか
- 「依存関係」の情報と、「変更内容の要約」に矛盾が無いか
- 「変更スコープ」で列挙したパッケージのうち、「変更内容の要約」で根拠や意図が説明されていない物が無いか。説明されていない変更は、未説明の変更として注意点に書く

## レポートの出力

[TEMPLATE.md](TEMPLATE.md) を読み込み、その構成でレポートを作り、指示された出力先に出す。Reviewerには自分のAgent名とmodel名を書く。GitHubに載る文章の書き方は、`kuden:github` skillに従う。

ラベルの名前を指示された時は、レポートをpull requestに投稿したらレビュー依頼のラベルを付け、セキュリティ更新としたレポートにはセキュリティ更新のラベルも付ける。結論が「判断保留」の時は、レビュー依頼のラベルを付けない。

## 報告

起動した指揮役かユーザーに、短く報告する。詳細はレポートにあるので、繰り返さない。

- レポートを出力した場所と、結論。投稿したコメントのURLや、書いたファイルのパスである
- 付けたラベル。付けた時だけ
- 「興味深い更新」の節に内容があるか
- 確認できなかった事と、手段が無くてできなかった事
- 手順で曖昧だった点

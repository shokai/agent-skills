# ソフトウェアテストを書く時の心得

testを書く時、足すかどうかを決める時、落ちたtestを直す時、レビューする時は、以下の基準に従う。assertの流儀、ファイルの置き場所、test runnerといった書き方は、repoの既存のtestとドキュメントに従う。

## 心得1. 守りたいラインを決めて、そこだけに最小限書く

testは、そのPRが正しい事の証明であると同時に、別の変更によって壊されないように守る物である。守りたいラインを決めて、将来壊れるだろう場所を予測して、そこだけに最小限書く。

- 「別の機能追加によって壊されるかも」と思った箇所に重点的に仕込む。別ファイルの関数1つだけをimportしている箇所、ファイルの読み込み順や関数の登録順に依存する箇所、依存ライブラリの更新で挙動が変わる箇所がこれに当たる。開発者は機能Aと機能Bは無関係だと思っているが、実はどこかで関係している事がある
- 壊れても問題ない部分にはtestを書かない
- 守るラインを決めずに書くと、testは際限なく増える。仕様変更の度にtestの大半を書き直す事になり、その作業でミスが入ってお漏らしするので、testが実質的に何も守ってくれない状態になる

## 心得2. お漏らししてないかを重点的にtestする

ラインには、守られている側と越えられた側がある。越えられた時に、被害を受けた人が気付かない、または報告してくれない側を優先してtestする。

権限がある人がアクセスできる事のtestは、書かなくても実害が出ない。不具合があっても、アクセスできるはずの人ができないだけで、その人は「見れないんですけど」と報告してくれる。権限が無い人のアクセスを拒否するtestが無いと、権限が無い人がアクセスできてしまう。その多くは報告してくれない。自分には権限があって正常に見えているだけだと思っているか、報告が面倒か、他人の非公開情報が見えても自分に実害が無い。クリティカルな実害が発生してからようやく報告が来て、謝罪プレスリリースを出す事になる。

- 必要なラインギリギリを見極めて、その危険側を集中的にtestする。project memberだけが読めるページなら、ログインしているがmemberではない人がアクセス拒否される事をtestする。ログインしていない人で試すと、ログインしている・していないの境界をtestした事になる
- 権限がある人に200が返る事のtestだけでは、ほとんど何も守れない。権限が無い人にも200が返っているかもしれない。書く余裕があるなら書いてよい
- 全組み合わせを網羅せず、権限の境界の最小セットだけ書く。誰でも読めるpublic projectの読み取りなら、最も権限が低い人が通る1件で足りる
- 認証を付けたら、認証がかかっている事のtestをセットで書く。middlewareの変更やリファクタリングで認証が外れても、動作確認とレビューでは気付けない。ログインしていない場合と、他人がログインしている場合を確かめる
- 権限以外でも同じ。一括削除が隣のtenantにある同名のデータを消さない事、非公開に切り替えたデータが外部向けの出力に出ない事、通知を送ってはいけない相手に送られない事
- 実装側では権限がある事を確認し、test側では権限が無い人が拒否される事を確かめる。権限の種類は将来必ず増え、権限がある事を確認する実装なら、増えた権限の人にはデータが返らないので安全側に倒れる

## 心得3. データ形式のtestとアクセス権限のtestは分けて書く

- アクセス権限のtestは、controllerにリクエストしてstatus codeだけを見る。pathとユーザーの種別と期待するstatus codeの組み合わせの表として書くと、一気に確かめられる。メンテが大変でなければ、境界ギリギリ以外も充実させてよい
- データ形式のtestは、methodの返り値を見る。HTTPや権限を混ぜない
- 単純なAPIならまとめてtestしてよい。複雑なAPIで混ぜると、判定のパターンの数だけ中身の検査も増える
- 超重要ではない機能で、レスポンスにfieldが存在する類のtestは書かない。書き始めるときりが無い。防ぎたいのは情報漏洩なので、拒否の検証に集中する。使っていれば分かる程度の不整合は、見つけ次第直せばよい

## 心得4. 実装の写しになるtestを書かない

正常系のtestを無限に足すと、実装のただのコピーになる。実装を変える時に二重に書き換える事になり、変更コストを上げるだけで何も守らない。

- 定数配列や、外部の関数を1回呼ぶだけのラッパーにtestを書かない。testを足すかは、条件分岐・状態・正規化・パース・計算といったロジックがあるかで決める
- 文字列の整形やメールの文面のtestを書かない。templateの再記述にしかならない。escape漏れはtestではなくレビューで確かめる
- schema validatorが正しく書けている事を確かめるだけのtestを書かない
- 処理の呼び出しを消しただけの修正に、消した処理が実行されない事を確かめるtestを書かない。実装を読めば分かる
- bugがあっても安全側に倒れる実装にtestを書かない。bugがあっても、表示されるべき物が表示されなくなるだけで、お漏らしにはならない除外処理がこれに当たる
- bug修正で、修正の正しさを確かめる正常系のtestを「念の為の回帰防止」として残さない。手元の実行で確かめる。残すなら異常検知に限る。「将来誰かが再導入したら検出できる」は弱い動機で、実装のコピーになっていないか自問する
- testを足す前に、実装の量と釣り合っているか、bugがあった時に何が起きるかを考える。bugの帰結が情報漏洩や権限の逸脱のような危険側なら異常検知のtestを検討し、表示が減る・処理が呼ばれないだけの安全側なら書かない

## 心得5. testを通すために、実装やtestの仕組みを曲げない

testは、実装が正しいかを確かめる為にある。testが落ちた時に、testを通す事だけを目的に、実装・期待値・testの根本的な方針や機構を曲げない。

- 落ちたtestの期待値を変える時は、実装の意図との食い違いを説明する
- test runnerの移行やリファクタリングの前後で、testの合計件数が変わらない事を確かめる。件数を減らす時は、減った件数と理由を明記する

## 心得6. fixtureの仮名には、ユーザー自身のhandleを使う

test fixtureや設定の例で仮のメールアドレスやユーザー名を書く時、局所部には、作業を指示しているユーザー自身のhandleを使う。`taro` のような汎用的な人名は、実在の社内外の人物のアカウントと同じになると問題になる。自分のhandleなら、実在しても本人である。ドメインは `.example` か、既存のtestが使っている物に合わせる。

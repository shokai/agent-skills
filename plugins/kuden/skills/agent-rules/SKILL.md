# AI向けのルール文書を書く時の心得

CLAUDE.mdやAGENTS.mdのように、AIが作業の前に毎回読む行動のルール文書を作る時、編集する時、他所から規則を取り込む時は、以下の基準に従う。Agent Skillは、kuden:agent-skill skillの基準に従う。

## 心得1. 制約だけを書く

既定の挙動を制限・誘導する規則だけを書く。禁止が無ければ当然できる事を、許可として書かない。

## 心得2. 制約の文体は、提案を求めるかどうかで選ぶ

- 必要になった時にAIから提案してほしい操作は、「勝手に行わない。必要だと判断した時は、実行せずに提案して指示を仰ぐ」と書く。commit済みの履歴を書き換える操作がこれに当たる
- ユーザーの発意に委ねる操作は、「ユーザーの指示を待つ」と書く。pushがこれに当たる

## 心得3. 制約を作業の一場面に限定しない

操作全体に効かせる制約を、「Zの後のXは指示を待つ」のように作業の一場面に限定しない。止まった時に何を告げるかのような、その場面でのAIの振る舞いも書かない。開発の流れは一様ではなく、特定の場面を前提にした規則は、その前提から外れた流れで噛み合わなくなる。

## 心得4. 背景説明・比喩・理由を書かない

- 他所の文書から規則を取り込む時は、元に無い文を足さない
- 比喩を書かない。読み手が比喩の別の側面を推論し、規則が曖昧になる
- 「〜しないと古くなる」のような理由を書かない。規則の効力を増やさず、逸脱した読み手への説教にしかならない
- 見出しや参照元で既に示したスコープを、冒頭で繰り返さない
- draftは仕上げている途中の状態、ready for reviewは人間にレビューを依頼できる状態、のような状態の定義は書いてよい。規則の意味を定める

## 心得5. 同じrepoの中で、制約を2箇所に書かない

制約は、毎回読まれるルール文書の1箇所に書く。同じrepoの中で併用する作業手順の文書に、同じ許可条件を再掲しない。

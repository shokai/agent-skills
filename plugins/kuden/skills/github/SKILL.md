# GitHubでの作法

pull requestを作成・更新する時、GitHubに載る文章を書く時、レビュー指摘に対応する時は、以下の基準に従う。repoのドキュメントやPRテンプレートに別の定めがあれば、そちらに従う。

## 心得1. ready for reviewは、人間にレビューを依頼できる状態である

draftは実装者が仕上げている途中の状態で、AIによるレビューはこの間に済ませる。ready for reviewを、AIレビュー待ちの意味で使わない。

- PRはdraftで作る。そのrepoの過去のPRがdraftを経ていなくても、draftで作る
- draftの間は、人間にレビューを依頼する見た目を作らない。reviewerを指定せず、レビュー依頼を表すラベルも付けない。reviewerの指定を拾ってラベルを付ける自動化があるrepoでは、指定した時点で人間のレビュー待ちの列に並ぶ
- ready for reviewへの切り替えは、ユーザーの指示を待つ
- 切り替える時に、そのrepoでレビュー依頼に使っているラベルやreviewerの指定を同時に行う。切り替えただけで放置しない。何を使うかは、repoのドキュメントやmerge済みのPRから読み取る

## 心得2. タイトルには、何を解決したかを書く

タイトルを書く前に、なぜ変えるのかと、この変更で何がどう変わるのかを1文にする。理由と、挙動がどう変わるかが書いてあれば、レビュアーはタイトルだけで妥当性の見当が付く。

- 実装の手順をなぞらない。そのPRで新しく作った関数名やファイルパスを並べたタイトルは、diffを読むまで意味が分からない
- 症状を消すとだけ書かない。「warningを消す」は握り潰しとも読め、変更の性質が伝わらない。「findOneAndUpdateのnew: trueはdeprecatedなのでreturnDocument: afterを使う」のように、理由と置き換えの中身を書く
- ユーザーに見えるbugの修正は、「<再現条件>と<症状>問題を修正」の形で書く。どう直したかは、概要欄の1行目に置く
- 画面に関わる変更は、実装の語ではなく、影響する画面の名前で範囲を示す
- 既存のtoolに出力を1つ足すような小さな変更は、理由を付けず、既存のファイル名やfield名で短く書く。理由を付けて長くなるなら、理由は概要欄に回す
- 文末の時制や区切り方は、そのrepoのmerge済みのPRに合わせる
- squash mergeではタイトルがcommitになる。commit messageの1行目も同じ基準で書く

## 心得3. 概要欄には、diffから読めない事を書く

概要欄に書くのは、目的、背景、問題と修正方針、動作確認方法である。追加した節の中身や新しい規則の内訳のような、diffを読めば分かる事実を列挙しない。

- 動機には、そのPRが直す問題だけを書く。調査のきっかけになった別の問題の経緯は、指示元へのリンクに任せる。本題と関係ない文脈は、本題の説明を邪魔する
- コード全体に効く欠陥の修正を、それに気付いた特定の実行の物語で始めない。書き終えたら、変更の主目的が症状の抑止に見えないかを読み直す
- 達成したい事の水準で書く。個々の機能の入力と挙動を網羅するのは、helpやAPI documentの役目である
- 特定の行や関数への変更理由は、その行に付けるインラインレビューコメントに任せ、概要欄に重ねて書かない。概要欄をレビューする時も、インラインレビューコメントで説明済みの事を、書かれていないと指摘しない
- 最後に動作確認方法を置き、レビュアーが手元で確かめる手順を書く。AIが済ませた検証は、それとは別の節に分ける

## 心得4. リンクが壊れない書き方をする

概要欄、コメント、commit message等、GitHubで表示される文章の全てに当てはまる。

- `#1234` やURLの前後には、半角スペースを入れる。`#1234で直した` はリンクにならない。`(https://example.com/日本語のページ)。` は、`)。` までがURLに含まれる
- `#数字` は、issueとPRの番号にだけ使う。Dependabot alertのように別の番号体系を持つ物は、フルURLで書く。`#数字` で書くと、同じ番号の無関係なissueやPRへのリンクになる
- 日本語を含むURLは、percent-encodeせずに書く。encodeしたURLは、どのページへのリンクかを人間が読み取れない
- 括弧を含むURLは、Markdownのリンク記法で包まず、そのまま書く。リンク記法の括弧と衝突して壊れる

## 心得5. sub pull requestは、親子の両方からリンクする

- 親PRの概要欄に `## sub pull request` の節を置き、sub PRを作る度に `- #1234` の形で足す
- sub PRの概要欄の1行目に、`#1234 に向けたsub pull requestです` と書く
- 親branchは、mainに空のcommitを1つ積んで作り、draftの親PRにする。差分が無いとPRを作れない
- sub PR同士は兄弟にする。あるsub PRのbranchから次のsub PRを作ると、先のPRのcommitがdiffに混ざる
- PRをどこに向けるかをユーザーに訊く時は、branch名ではなくPRの関係で訊く。「`feature-x` からbranchを切るか」ではなく、「#1234 に向けたsub PRにするか、mainに向けたPRにするか」と訊き、本番に載る時期のような帰結を添える

## 心得6. 人間が並行して編集している前提で扱う

PRのタイトル、概要欄、コメントは、人間も直接編集する。

- 書き換える直前に現在の内容を取得し、自分が最後に書いた版と比べる。違っていれば人間の編集なので、その版を土台にして自分の変更を当て直す。手元に持っていた版を使い回さない
- 「おかしい」と言われたら、何がどう変わったのかを編集履歴で確かめてから直す
- 戻す時は、履歴にある直前の値に戻す。自分が覚えている版に戻すのは、復元ではない
- 複数のPRを、同じ操作で一括して書き換えない。1つずつ現在の内容を見る

## 心得7. レビュー指摘は、現在のコードに当てはまるかを確かめる

レビューコメントは、投稿された時点のコードへの指摘である。対応する前に現在のファイルを読み、指摘がまだ当てはまるかを確かめる。後のcommitで改訂済みの箇所を当時の指摘の通りに直すと、既に選ばれた解決を壊す。

## 心得8. 付随的な小さい修正は、今のbranchで直す

作業中に見つけた1行程度の既存の誤りは、別のbranchを切らず、今のPRのbranchに独立したcommitで入れる。変更が大きい時や、レビューの論点が増える時は、別のPRを提案する。

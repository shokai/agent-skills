# 発見のトリアージ

codepatrol skillの指揮役から任されて、調査レポートの発見を分類し、トリアージページを作る。

レポートの発見が多い時、どれを誰が直すかを決める材料にする。深刻度の付け直しや、発見が再現するかの確認はしない。それらは調査で済んでいる。

## ファイル構成

```
{このSKILL.mdがあるディレクトリ}/
  SKILL.md               ← この手順書
  TRIAGE-TEMPLATE.md     ← トリアージページのテンプレート
```

## このskillを実行する時の前提

- ユーザーに質問できない。判断がつかない事は、最後の報告に書く
- コードは読まない。レポートに書かれた内容から判断する
- 書き出し先がCosenseの場合だけを扱う。`.dev/codepatrol/config.md` の書き出し先がローカルの時は、対応していない事を報告して終了する
- Cosenseの読み書きは、cosense skillに従う

## 分類

修正に必要な仕様の判断を、誰が下す必要があるかで、次の3つに分ける。分類の名前は、この文をそのまま使う。

1. 仕様を変えるための判断が要らず、実装者だけで直せる不具合
2. 仕様を変えるための判断が要るが、レビュアーへの説明は容易な不具合
3. データモデルやセキュリティモデルが大きく変わる、利用者への周知が要る等で、設計から見直す必要がある不具合

1は、その製品に詳しくない実装者でも直せる。3は、その製品の開発者自身が、後の事を考えながら設計を直す必要がある。

- 1でも、実装の中で小さな判断は発生する。不正な入力にどのステータスコードを返すか、といった判断である。実装者がその場で決められる判断は、1に含める
- 変更の量では分けない。差分が小さくても、チームの合意が要る物は2である
- レポートの発見にある対応の記述が、判断の材料になる。修正方法が具体的に書かれているか、設計の変更が必要と書かれているかを見る

## 対象

各領域の最新のレポートを対象にする。hubページに集約されたレポートのうち、領域ごとに最も新しい物である。

載せる発見の条件は、指揮役の指示に従う。指示が無ければ、深刻度がHighの発見を対象にする。

## ページを作る

[TRIAGE-TEMPLATE.md](TRIAGE-TEMPLATE.md) を読み込み、その構成に従って新しいページを作る。

- 複数のレポートが同じ根の問題を報告している時は、1行にまとめる。どちらの名前で扱うかがレポートに書かれていれば、それに従う
- 1件の発見を、修正の単位で分けた方が分類しやすい時は、行を分けてよい。仕様の判断が要らない部分と、要る部分が混ざっている発見である
- 完全に修正された発見は載せない。完了した物が並ぶと、未処理の発見の数が分かりにくくなる
- 一部だけ修正された発見は、残っている事を載せる

### 前のトリアージページがある場合

前のページを編集せず、新しいページを作る。前のページの冒頭に、新しいページへのリンクを1行だけ足す。前のページの他の行は編集しない。

前のページの全ての行について、行き先を決める。黙って消える行を作らない。

| 最新のレポートでの状態                                           | 行き先                                                 |
| ---------------------------------------------------------------- | ------------------------------------------------------ |
| 今回も対象の条件に合う                                           | 分類の節に載せ、前回から継続している事を書く           |
| 全部が修正された事を、レポートが確認している                     | 載せない                                               |
| 深刻度が変わり、対象の条件から外れた                             | 末尾の節に、名前とリンクだけを載せる                   |
| 「今回検出しなかった前回の発見」にある                           | 末尾の節に載せる。修正されたという意味ではない事を書く |
| コード上は修正されたが、コードからは確認できない作業が残っている | 末尾の節に載せる                                       |

レポートの「前回から修正された物」の節には、一部が修正されて深刻度が下がった発見も並んでいる。この節にある事だけでは、載せない理由にならない。

前のページから引き継ぐ物と、引き継がない物がある。

- 人間が書いた注記は、対応する行に、文言も署名も変えずに引き継ぐ。優先度の判断や、着手の宣言である
- 作業中の修正pull requestの行は、そのまま引き継ぐ。pull requestの実際の状態は確かめない。状態の確認はcodepatrol-sync-stateが行う
- 分類の節には、前のレポートへのリンク、前のトリアージページの行へのリンク、完了した修正pull requestを引き継がない。リンクは最新のレポートの物に差し替える。古いリンクが並ぶと、どのレポートを見ればよいのかが分からなくなる
- 末尾の節の行は、その発見の根拠が書かれているレポートにリンクする。最新のレポートに無ければ、前のレポートである

### タイトル

`{hubページ名} トリアージ {YYYY/M}` とする。同名のページが既にある時は、年月を年月日にする。前のトリアージページが別の規則でタイトルを付けている時は、それに合わせる。

## 指揮役への報告

- 作成したページの場所とタイトル
- 対象にしたレポートの数と、対象の条件
- 分類ごとの行の数
- 同じ根の問題としてまとめた発見
- 前のトリアージページの行の行き先ごとの数
- 分類に迷った発見と、迷った理由
- 判断がつかなかった事

# 自動修正の指揮

トリアージページの問題を、subagentに1つずつ修正させ、pull requestを積み上げていく。修正の作業が続く間、指揮役は問題を選び、subagentを起動し、報告を確かめ、mergeされた後の処理を任せる事を繰り返す。

人間は修正の途中に立ち会わず、出来上がったpull requestを後からまとめて確かめる。どの問題を、どこまで人間の確認なしで進めるかは、ユーザーが決める。指揮役は、決められた範囲を自分では広げない。

## 前提

- 書き出し先がCosenseで、修正する問題を載せたトリアージページがある。無ければ、先にトリアージを行う
- 「実行環境の確認」の3つの条件を全て満たす
- `software-factory-mode-2026aki` skillのSKILL.mdが読める。修正するsubagentが従う開発フローである。Skill toolでは呼び出せないskillなので、installされたpluginのファイルから探す。見つからなければ、installをユーザーに依頼して止まる
- 始める前に、状態同期を行う。ページの状態が古いと、他の人が直した問題に着手する

開発環境の用意、testの実行、レビュー依頼の慣習といったrepo固有の手順は、repoのドキュメントや、ユーザーが残した記録にある物を使う。場所を把握し、subagentへの指示に含める。

## 何を自動修正するかを決める

問題は、レポートが付けた深刻度と、トリアージの分類の、2つの軸で分かれている。どの組み合わせを自動修正するかを、AskUserQuestionツールでユーザーに訊く。

- 最初は、深刻度Highの分類1を勧める。他の候補として、深刻度Mediumの分類1を挙げる
- 選ばれた組み合わせに、着手できる問題が無くなったら、次の組み合わせを訊く
- 分類2や3は、選択肢には挙げるが、指揮役からは勧めない
- 2つの軸の意味や、自動修正の考え方は説明しない。ユーザーは理解している。組み合わせを挙げて訊くだけでよい

勧められる範囲は、自動修正の副作用で決まる。自動修正は、人間が下すはずの判断をAIに任せるので、問題は直っても別の不具合を起こす事がある。

- 分類1の問題は、セオリーに従って実装すれば、副作用はほぼ出ない
- 分類2の問題は、副作用が多くなる
- 分類3の問題は、さらに、設計に禍根を残す恐れがある
- 深刻度が高ければ、副作用を飲んでも直す価値がある。深刻度が低いと、副作用の方が重くなりうる

副作用をどこまで許容するか、修正の中身への人間の理解をどこまで手放すかは、その時の状況で変わる。インシデントの対応中は許容の幅が広がる。決められるのは人間だけである。

分類2や3を含む組み合わせが選ばれた時は、subagentからの質問の取り次ぎが大量に起きる事を伝え、どう進めるかを訊いてから始める。

## どこまで自動で進めるかを決める

2つの段階がある。最初にユーザーに訊き、ready for reviewまでの段階から始める事を勧める。mergeの自動化は、ユーザーが出来上がったpull requestの様子を見てから上げる物である。作業の途中でも、ユーザーの指示があれば切り替える。

| 段階                 | subagentが行う事                           | mergeする者                               |
| -------------------- | ------------------------------------------ | ----------------------------------------- |
| ready for reviewまで | pull requestをready for reviewまで仕上げる | 人間                                      |
| mergeまで            | 同じ                                       | 指揮役。CIが通ったpull requestをmergeする |

### mergeまで進める時の、pull requestの向け先

修正のpull requestは、mergeしても即座には本番に出ないbranchに向ける。人間が、本番に出す前に、積まれた修正をまとめて確かめられるようにする。

- default branchにmergeした物が、release PR等を経てから本番に出るrepoでは、default branchに向ける
- default branchにmergeすると即座に本番に出るrepoでは、修正をまとめる親PRを作り、修正のpull requestをそのsub pull requestにする。作り方は `kuden:github` skillに従う
- どちらのrepoなのかが分からなければ、ユーザーに訊く

release PRと親PRは、指揮役もsubagentもmergeしない。本番に出すのは人間である。

mergeするのは、subagentがready for reviewにし、CIが通ったpull request全てである。subagentが「人間が確認すべき事」を報告していてもmergeし、その内容をユーザーに伝える。

次のpull requestはmergeせず、ready for reviewのまま残して報告する。

- mergeすると即座に本番に出るbranchに向いている。mergeの直前に、pull requestの実際の向け先を確かめる。ready for reviewまでの段階で作られた物は、段階を切り替えた後も、default branchに向いたままである
- CIが走っていない。結果が無い事を、通ったと扱わない。親PRに向けたpull requestでは、CIが走らない設定のrepoがある
- 人間が変更を求めている
- branchの保護等でmergeできない

## 起動を止める上限

人間の確認を待つ修正が溜まりすぎると、pull request同士が衝突し、まとめて本番に出す量も増える。上限を最初にユーザーに訊き、達したら新しいsubagentを起動しない。進行中のsubagentは完走させる。

| 段階                 | 数える物                                                                                |
| -------------------- | --------------------------------------------------------------------------------------- |
| ready for reviewまで | 自動修正で作った、mergeされていない問題                                                 |
| mergeまで            | release PRや親PRに積まれ、本番に出ていない修正の問題。mergeを見送って残した問題も数える |

数えるのは問題で、pull requestではない。1つの問題の修正が、複数のrepoのpull requestになる事がある。ready for reviewまでの段階では、5件を目安として勧める。

## 問題を選ぶ

選ばれた組み合わせの中で、直しやすい問題から着手する。レポートに対応の案が具体的に書かれている問題である。

次の問題には着手しない。

- トリアージページの行に、他の人の着手の宣言や、pull requestがある
- 残タスクとして、判断が必要である事が申し送られている。前の修正が、実装してみて仕様の判断が要ると分かった物である
- 進行中の修正や、mergeされていないpull requestと、同じファイルを触る。後に回す

進み具合は記録に残さない。起動し直した時は、トリアージページの状態とpull requestの実際の状態から、残りの問題と、確認を待つ修正の数を求め直す。問題が多い時は、候補を読んで順番を付ける作業を、subagentに任せてよい。

自動修正で作った修正は、トリアージページの行の署名で見分ける。AIの署名に、このユーザーの署名が並んだ行である。

起動し直した時に、自動修正の署名が付いた行に、着手の宣言や、draftのままのpull requestが残っている事がある。前のsessionで途中のまま止まった修正である。pull requestのコメントとレポートの申し送りから、止まった理由を読む。

- 利用上限やCodexの停止のように、作業の都合で止まった修正は、新しい問題より先に、新しいsubagentに引き継がせる
- 質問や、別の重大な問題のように、ユーザーの判断を待って止まった修正は、再開させない。ユーザーに伝えて判断を待つ
- 止まった理由が分からない修正と、他のsessionが進めているかもしれない修正は、ユーザーに訊く

署名の違う行は、他の人の作業である。draftのまま動いていなくても、引き継がない。

## 修正をsubagentに任せる

問題1つごとに新しいsubagentを起動し、codepatrol-autofixを実行させる。並列は3本までにする。

複数のsubagentが共有する開発サーバーやコンテナは、指揮役が起動し、作業が全て終わったら止める。subagentには止めさせない。

### 指示に含める事

- 担当する問題の名前と、レポートの問題への行リンク、トリアージページの行へのリンク
- 途中で止まった修正を引き継がせる時は、引き継ぎである事と、残っているpull requestやbranch
- `software-factory-mode-2026aki` skillのSKILL.mdの場所
- pull requestの向け先。親PRに向ける時は、親PR
- 仕様の判断が要る時の扱い。ユーザーが決めた時だけ含める
- ユーザーの署名。subagentが、ページに自分の署名と並べて書く
- 作業用ディレクトリ。session用の一時ディレクトリの下に、問題ごとに分ける
- 並走している修正と、それが触るファイル。関連する、merge済みのpull request
- repo固有の手順の場所

## subagentの報告が来たら

報告は自己申告である。pull requestの実際の状態を自分で確かめてから、ユーザーに短く伝える。直した事、レポートの対応の案と違う判断、人間が確認すべき事である。人間が確認すべき事は、省かずに伝える。mergeまで進める段階では、mergeの前にユーザーがそれを知る機会が他に無い。

- 質問で止まったsubagentには、ユーザーの答えを渡して再開させる。新しいsubagentを起動しない。途中結果を引き継げる
- subagentが、sanity-reviewの完了を待つ途中で報告を返す事がある。sanity-reviewの報告は指揮役に届くので、それを渡して再開させる
- mergeまで進める段階では、mergeの条件を確かめてmergeする

## mergeされたら

人間がmergeする段階では、mergeされた事は知らされない。pull requestの状態を定期的に確かめる。

mergeされたpull requestについて、次の3つをまとめて1つのsubagentに任せる。複数のpull requestをまとめて任せてよい。

1. 開発環境の後始末。`software-factory-mode-2026aki` skillの「開発環境の後始末」に従う。修正したsubagentが報告した、残した作業環境を渡す。どの修正の物か分からない物は、消さずに報告させる
2. 状態同期。codepatrol-sync-stateを実行させる。範囲は、対象のpull requestの行だけでよい
3. deploy noteの更新。codepatrol-deploy-noteを実行させる。release PRや親PRのように、本番に出る前の修正が積まれるpull requestがある時に行う

報告は短くさせる。空いた分だけ、次の問題の修正を起動する。

deploy noteは、人間が書いた確認も反映する。mergeが無くても、起動し直した時と、作業を終える時に更新させる。

## 止まってユーザーの判断を待つ

- 起動を止める上限に達した
- Codexが止まり、subagentが作業を中断した。Codexを使わない修正に切り替えない
- subagentが、修正を入れると別の重大な問題が起きると分かって止まった
